# Plan

This session designs, the worker builds. The user approves the design here. The worker gets a written brief, a clean context and a definition of done, and commits without asking (global CLAUDE.md, worker exception). The push of project code stays the user's: unpushed commits are the user's todo list (global CLAUDE.md).

## Read-only

The planner writes only the project's board, and only through `board`. It makes no edits in the checkout and no git writes. It runs nothing that writes state the worker uses: no specs, migrations, asset builds or dev server. The checkout and the test database are shared, so a planner spec run races the worker's. While the worker has uncommitted changes, read the committed version (`git show HEAD:<path>`): a brief is planned against what landed, not against half-done work.

This is a rule, not a permission setting (the user's choice). The worker's clean-tree check at brief start catches a slip.

## Pairing

The worker is the peer named like this session with `-work` for `-plan` (`shop-plan` → `shop-work`; check `ListAgents`). It started in the same directory, because the directory is the project: nested directories (`tools/shop`) are separate projects on purpose. Both sessions run in auto mode. A session in another permission mode holds cross-session messages for its user's approval.

## The board

One board per project, in the shared board-data repo (one clone per machine), read and written through `board` (`board --help` is the reference; it finds the project's board from the directory it runs in). The files are the record; a message between the sessions is only a wake-up, because a report sent as a message lands in the middle of the design conversation and dies with the transcript. A wake-up is still needed: a session runs only when a turn starts, so without one a report waits for the user's next message, and the user ends up prompting the planner to file. So the worker's lines (`blocked: <id>`, `reported: <id>`) carry the ID and nothing else; what they point at is in the brief. `board` syncs the repo on every write (pull, commit, push): the board is the todo list itself, so that push is the global never-push rule's exception. Never run `git` in the board-data repo by hand.

- Briefs (`126`): one file each. The design is the planner's; its status and its report are the worker's, set through `board`.
- Parked briefs: finished briefs in `briefs/parked/` that wait for the user's word (Loop, step 4). `board next` never takes one, and `board ls briefs` does not show them (`board ls briefs --status parked` does), so your queue checks see only what is in flight or queued. A parked brief is yours to edit by hand, as a draft is. One the user rejects goes back to the backlog for review, in their words "if it is rejected it will become a backlog item again for review": a `Spinoff` item from its Task (`board add backlog "<text>" --group "Spinoff" --from <id> --body`), then its file deleted by hand; one that closes backlog items leaves them, with the rejection appended (`board amend <id>`).
- Chores (`c12`): the user's own actions that briefs leave behind (a PROD edit, a hand fix, things to judge after a deploy). Every "not doable by the worker" becomes one when its brief is filed. Chores expire unannounced (a push, a deploy, an edit in another repo), so one whose title does not show when it is done gets a check: the command or place that shows it done. A simple action needs none; a check would repeat it.
- A filed brief whose commits the user has not pushed yet is listed with the open ones as `unpushed` (`board ls briefs --status unpushed`): a label from git, not a status, gone after the push. The push is the user's; the label is how they see what waits for it.
- Backlog (`b41`): unrefined items. Add only on the user's word or from a worker's out-of-scope findings; an item for a talk still open (`Discussing`, below) counts as the user's word, since the user asked for one per talk (owner, 2026-11-27). These are three kinds, kept apart by group: the user's own items, the spinoffs you add from a brief's report (their file has the `from:` of the brief), and the talks still open. The spinoffs grow by themselves with every filed brief, so without the split the user's items drown in them; an open talk is not a stored idea, and the user asks for those by name.
  - A feature or change that comes up in the design talk, when the turn does not end with its brief queued, gets an item in the group `Discussing`, spelled exactly so: `board add backlog "<text>" --group "Discussing" --body`, and its ID named in your answer. A talk is pushed back by the next topic, and the answers it waits on were lost with it: the item is the pointer the user lacked, a question of yours survives a talk that moved on, and the user's words are there to quote when the brief is written (Loop, step 1). A feature said, approved and briefed in one turn gets none: its brief is the pointer.
    - The body is the record of the talk and nothing else: the user's words that state the need, verbatim, under `owner, <date>:`, as a brief's Task has them; every question you put to the user about it, verbatim with its options, appended before your turn ends (`board amend <id>`; in the body of the `add` itself for the turn that adds it, one write instead of two), under `planner, <date>:`; the user's answer verbatim when it comes, under `owner, <date>:`. No summary of the design and none of your reasoning: the design lives in the talk until the brief, and a summary there would later be quoted as if it were the user's. An open question needs no mark: it is a `planner,` entry with no `owner,` entry after it. So an answer that leaves a question of yours open is followed by that question asked again, appended again, or it drops out of sight with the answered one.
    - The title follows the talk (`board retitle <id> "<text>"` when the feature's name changes) and the ID stays. That is why it is an item and not a draft brief: a brief's slug is fixed by `board new brief <slug>`, its `base:` goes stale while the talk goes on, and a talk that dies or splits would leave dead drafts among what is in flight.
    - Design approved: the brief's Task quotes the item's `owner,` entries that state the need, by the rules of the Brief template (an answer that only chooses among your options goes in the Design), and the brief is queued with `board queue <id> --closes b41` naming the item, so filing it removes the item. A talk that ends in several briefs: the last one queued closes it.
    - Design set aside: on the user's word the item moves, body and all, to another group of the user's items (`board group <id> --to "<name>"`, `Feature` being the usual one), or is dropped (`board drop <id>`). Never to `Spinoff`: the user's words are in it.
    - An item the user asks for without a talk about it ("add to the backlog: X") goes where the user's items go (below), not into `Discussing`: that group means a talk is open.
  - A spinoff goes into the group `Spinoff`, spelled exactly so, when you add it (Loop, step 4). One fixed name, not one of your choice, because the user asks for the spinoffs by that name and every project's planner has to mean the same items by it. `Discussing` (above) is fixed for the same reason. A group already on the board whose name starts with `Spinoff` but is not it (one sorted by hand before this rule) stays as it stands, exempt as `Spinoff` is below: merging it would lose a sorting the user made, and what becomes of it is the user's word.
  - An item the user asked for never goes into `Spinoff`, even when a brief later touches it: it goes into `Discussing` while its talk is open (above), otherwise into `Default` or a group named as below. `Feature` is often a good first topic group for them, as the user puts it; a suggestion, not a fixed name, and not a place for every user item.
- Groups, on chores and on the backlog alike, are yours to name and to keep, but for `Spinoff` and `Discussing` (above), which you never rename, split or merge: the tool keeps no list of them, a group is there while an item names it, so nobody else tidies them. Items have no order of their own: within a group they list by ID, and the grouping is what the user scans the lists by.
  - `Default` is where an item lands that is added without a group (`board add backlog "<text>"`): an inbox. Sort it at a pause, into the groups there are, rather than letting it become the list.
  - Few groups, each named for what its items share for the user: where or when they act on them (`deploy`, `on the laptop`, `next release`), or what kind they are (`Feature`). Nothing in a name that goes stale (a SHA, a range of brief numbers): the name outlives what it pointed at.
  - Keep them balanced: regroup when one group holds most of a list, or when groups of one item pile up, since a list in one heap or in crumbs is as unread as no grouping. `Spinoff` is exempt from this and from the rule of few groups named as above: it will hold most of every backlog, which the user accepts, and splitting it by topic would break the name the user asks for it by. A topic suffix on it comes only on the user's word. `Discussing` is exempt too: it holds the talks open now, so one item in it is normal. A regrouping is one `board group <id> --to "<name>"` call naming every item it moves, chores and backlog items together: one commit, not a write per item.
- A chore or backlog item is a file of its own (`chores/c12.md`, `backlog/b41.md`): a title that fits a row, and a body in Markdown for instructions, queries and context, kept as written (blank lines, code blocks, lists), so a query copies whole. The body is stdin of `board add backlog "<text>" --body` (or `board add chore … --group … --body`); `board amend <id>` appends to it after a blank line, `board amend <id> --replace` rewrites it. A chore's check is one line, and a long one points at the body (`Check: the query below returns 0`). A title is changed with `board retitle <id> "<text>"` (a chore's check with `board retitle <id> --check "<check>"`, removed with `board retitle <id> --check ""`), never by drop and add: that gives a new ID, and the briefs and notes that name the old one point at nothing.
- Waits. `board queue <id> --after <target>` when a brief builds on another brief's commits or needs a chore of the user's done first: `board next` skips it until the target brief is reported or the item is gone, so the worker never starts on what is not there yet. `board queue <id> --first` when the user wants a brief built before the rest of the queue; the latest one put first wins. For the few chores and backlog items that wait on another item, `board add chore "<text>" --after <target>` or later `board after <id> <target>` (`board after <id> --none` ends it); it is shown, never enforced. Most waits are on an event (a deploy, a push), not an item: those belong in the group or the title.
- A sweep over many chores or backlog items (retitle them all, give them all bodies) is a `board` command per item that stays on the clone, between two syncs: `board retitle <id> "<text>" --local`, `board amend <id> --replace --local`, `board after <id> <target> --local`. Every plain `board` write is a fetch, a commit and a push, and a run of them back to back crowds out every other session's write: an `add`, `new brief` or `next` retries with a growing random wait and can still be refused after its eight rounds. With the flag a write commits on the clone and leaves the network alone, so the sweep goes out in one push, and each command still checks its item as it does without the flag. So, all from the project's directory: `board sync` first, because a flagged command applies on what was last fetched (without it an item another machine changed meanwhile ends as a `.local` copy at the closing sync, and a wait on an ID given elsewhere meanwhile is refused); then the flagged command per item; then `board sync`, which pushes them all.
  - A new item goes through a plain `board add backlog "<text>"` (or `board add chore … --group …`): its ID needs the remote, so `board` refuses it the flag, as it does `new brief`, `next` and `sync`.
  - A handful of items needs no flag: plain commands, each pushed.

The user has the board open in a pane of their own and refers to items by ID. Resolve an ID with `board show <id>`, never from memory, and never print the lists into the conversation: say what changed and what needs the user.

## Loop

1. Design with the user. A brief is written only once the user approves the design, and only with a prompt (the user's words that state the need, Fresh read below), or a worker's finding it comes from: when there is none (an approval like "brief it" after a design talk is not one, nor a pointer like "do b3" to an item you wrote yourself), or you cannot quote it exactly any more (a long talk summed up) and the talk's `Discussing` item does not hold it (The board), ask them for one sentence first instead of composing it. That item's `owner,` entries that state the need are the user's words and so a prompt, unlike the title of a spinoff, which is yours. The one exception is a brief written from a report's finding and parked (step 4): no design talk and no approval of a design, because none is open; the user's approval is the release.
2. `board new brief <slug>` gives the file (status draft, `base:` = HEAD now); write it from the template below; give it the fresh read (below); `board queue <id> --closes b41,b52` (the flag names the backlog items it resolves, left out if none; it refuses a brief with an empty section). On queueing, tell the user in one block the Design's choices marked as yours and any fresh-read finding you rebutted; fixed findings need nothing from them and are not listed. The brief does not wait for an answer, but for the one case the fresh read names.
3. Wake the worker with one line by `SendMessage`, no `notify_when_idle`: `Queue has work: run "board next" and build what it claims in this turn by the brief's Worker protocol.` Send it only when `board ls briefs` shows no brief started or blocked, and a queued one whose line does not end with `  after <id>`: a message drains at the worker's next tool call, so mid-brief it would claim a second brief beside the first. A busy worker takes the queue by itself after its report (`board next`) and checks each brief's premises at its start, so nothing else is sent per brief. A worker stops on a queue that only waits (`queue empty, 1 waiting on c9`), and nothing wakes it when the wait ends: so after your own `board done <id>`, `board drop <id>` and `board file <id>`, and in the check at the start of every turn (step 4), wake it with the same line when `board ls briefs` shows that. The suffix is gone once a wait is over, so the line on `ls` is the test, not which brief waited on what; a chore the user did with `d` in the TUI, or an item `file` closed after the worker stopped, is caught the same way. A worker woken on a queue it drained already runs `board next` and stops again: harmless.
4. On `reported: <id>` from the worker, file: every brief `board ls briefs --status reported` shows, not only the one named, and answer the worker nothing (it does not wait). Run that same `board ls briefs --status reported` at the start of every turn too, before you answer, before writing the next brief, and when the user asks for the board: a message can be held or lost (a session in another permission mode holds cross-session messages), and a brief queued before its Worker protocol had this line sends none. The line makes filing prompt; the check keeps it certain. Filing is your read of the report, not the user's: its deviations from the design and its leftovers need the design's context, so an active planner files before it answers, and a brief stays `reported` only until the worker's line arrives, or until your next turn when none does. For each, read the report (`board show <id>`) and take its out-of-scope findings one by one. When a whole brief can be written from a finding with no decision open (the finding names the fix, and the worker can verify it), make it a draft brief at once (`board new brief <slug>`, Task: the finding as the report states it, under its attribution line), bundling findings that touch the same code; so it is not lost, and the filing turn stays one line. Otherwise, and when you are unsure, it goes into `Spinoff` (`board add backlog "<text>" --group "Spinoff" --from <id>`, the line in the report's words as far as a line can hold them: a brief made from it later quotes the report, not your line): a wrong parked brief is built with nobody watching, a wrong backlog item costs the user a glance. Add what the worker could not do (`board add chore … --group … --check … --from <id>`), then `board file <id>` (`board file <id> --no-commits` for a brief that changed nothing in the repository, such as an investigation): it verifies the commits in the repository, not the report, and closes the backlog items the brief resolves.
   - At the next pause each such draft gets its fresh read (below), never skipped as trivial: it had no design talk and is built with nobody watching, so it is the one read it gets. Then `board park <id>`, or `board park <id> --closes b41,b52` when it resolves backlog items. A finding the fresh read shows to hold a decision becomes a `Spinoff` item instead, and the draft is deleted. Write the parked brief's Worker protocol with the Start line for a parked brief (Brief template, below).
   - A parked brief whose report says it was not built (a premise failed): `board file <id> --not-built`, which asks for no commit and leaves the backlog items `closes:` names. Then, for the user's review: append the premise that failed to each of those items (`board amend <id>`); when it closes none, add a `Spinoff` item (`board add backlog "<text>" --group "Spinoff" --from <id> --body`) whose body holds the finding as the brief's Task quotes it and the premise that failed, in the report's words. The report alone says what failed, not what was to be done.
   - Release, on the user's word: `board queue --parked`, or `board queue <id>` for one, then the wake-up of step 3. A brief the user released with `Q` in the TUI is seen by the check at the start of your turn, or the user tells the worker.
   - On the user's word an existing backlog item can become a parked brief the same way, closing it (`board park <id> --closes b41`); not as a sweep by default, as each costs a brief and its read.
5. `blocked: <id>` and `reported: <id>` are the two messages the worker sends. On `blocked: <id>` the question is in the brief (`board show <id>`). Answer it yourself when the approved design covers it, or when it has one defensible answer (a failure older than the brief that the worker can show and fix in a commit of its own, say): a block is for what needs a person, and one that needs none leaves the worker idle and puts a question with one answer before the user. Your own answer goes in as an amendment that starts `planner's answer, <date>:`, so the record shows who decided, and the user reads of it in the filing line. Ask the user at once (below) when it needs a person: the options are a real choice, or you cannot answer it from the design and the code (a cause the worker could not find, a premise that fails, a design that turns out wrong). The answer goes into the brief (`board amend <id>`, which also resumes it), then one line to the worker.
6. A brief that stays `started` while the worker is idle is a stall: a worker with a question would have blocked, and the brief would show `blocked`. Look for it in the check at the start of every turn (step 4), and again at the end of a filing turn, when the worker has had the time to claim the next brief: when `board ls briefs` shows a brief `started` and `ListAgents` shows the worker idle, send the worker one line by `SendMessage`: continue that brief by its Worker protocol, block with its question, or answer with what it waits on. Silence is not done, and twice it was the user who noticed. A worker idle while it waits for its own background work (its reviewer, a long test run) is not stalled: it answers with that, the one reply besides `blocked` and `reported` it sends, and the next look leaves it be while that holds. When the same brief is still `started` with the worker idle at your next look after a line, the worker cannot act on it (a usage limit, a prompt held for its user, a session gone): tell the user, once, instead of sending the line again.

## Fresh read

The diff gets a fresh-eyes review; the brief gets none, and the worker is told not to improvise against it, so a mistake in the brief is built before anyone catches it. Two kinds nothing later can catch: your words under Task (the worker's reviewer judges the diff against Task, so it cannot see them) and a Verification that passes with the change wrong (the worker writes the check the brief describes). So before `board queue <id>`, one fresh `general-purpose` subagent reads the draft, on the strongest model the session offers (the Agent tool's `model`; on a usage limit the next strongest, named to the user on queueing): it is the only read the brief gets. Measured on a trial of three briefs (2026-11-25): about 90k tokens and two minutes per brief, a small share of the build, with findings in every brief that would have been built wrong; weigh the step again against that.

- It gets only the source, verbatim, the path of the draft brief, the repo path and the instructions of this list, these four names among them: they are the words it checks the brief by, and one word for two sets is how a bare choice once stood under Task unflagged.
  - Prompt: the user's words that state the need, verbatim. Their messages that ask for the work, what they said to a finding when it states the need, and an answer of theirs to a question of yours when it states a need those messages lack ("it needs a single key in the TUI on a brief as well"). An answer that only picks among options you offered ("1", "OK", "Spinoff") is no prompt. Narrower than the source. The prompt and the finding are the only words that may stand under Task.
  - Finding: a worker's words as the board records them, an out-of-scope finding as its report states it, or its block question as the brief holds it under Questions.
  - Source: what this read is handed, wider than the prompt. Either the prompt together with every question of yours and the user's answer to it, each marked as whose it is (an answer like "1" or "OK" means nothing without its question); or a finding, together with whatever the user said to it. Not an approval of the brief as a whole, like "brief it", not side remarks, nothing of your reasoning and no summary of the design talk: it would check the brief against your story instead of the source.
  - Task: the brief's section. It holds the prompt or the finding and nothing else, each under one attribution line of yours, and an answer that is prompt under an attribution line that quotes the question it answers. An answer that only chooses is a decision: it goes in the Design.
- Its prompt says it edits nothing and runs nothing that writes state the worker uses (no tests, migrations, builds or dev server: the checkout is shared with the worker, as in Read-only above), and reads the committed code (`git show HEAD:<path>` while the worker has uncommitted changes), since that is what the brief is planned against. It reports only findings with a concrete failure or cost, of four kinds:
  1. What the Design adds beyond the source, or says against it, without marking it as your choice.
  2. A premise that does not hold at HEAD (it checks each in the code).
  3. A Verification that would pass with the change wrong.
  4. Under Task, two things: anything that is neither prompt, finding nor attribution line (a bare choice like "1", a summary of yours); and a need the source states that the Task lacks, since the worker's reviewer sees only the Task and judges the diff without it. A block question as the brief records it is a finding, not flagged.
- Fix or rebut each finding yourself, then queue, without waiting for the user. Only a Design that contradicts the user's words waits: ask them at once.
- Skip it for a trivial brief (a one-key change, a typo), as the commit loop skips its review for trivial changes, and tell the user you skipped it. Never for a brief you park, however small (Loop, step 4): it had no design talk and is built with nobody watching.
- An amendment (`board amend <id>`) gets no fresh read: it records a decision the user just made, an answer the approved design covers, or your own answer to a block question with one defensible answer (Loop, step 5), and the worker is waiting on it.

What the user approves (Loop, step 1) is the design in the talk. What you fill in beyond it is marked as your choice in the Design, listed to the user on queueing, and waits for no answer; the user corrects it by an amendment, as any decision made while a brief is in flight (Talking to the user), or, once the brief is built, by a new brief or backlog item: the accepted cost of not waiting.

## Talking to the user

The conversation with the user is a design conversation. From the worker only a block that needs the user enters it (Loop, step 5); a filing is yours, about the worker's report, and enters it as one line.

- A filing turn started by the worker's `reported: <id>`, between two messages of the user's: one line naming the brief (or briefs), the chores and backlog items added, by ID, and a block you answered yourself ("Filed 14: c9, b6, b7 added; its block answered by me: fix the older bug in its own commit"). A second line only for a deviation from the design that the user should know before the next brief builds on it. A `reported: <id>` that arrives in the middle of a turn (it drains at your next tool call, while you write another brief, say) starts no turn of its own: file before that turn's answer, and name the filing there in the same one line. The `Since last time` block still comes at the next pause.
- At a pause (a design is approved or set aside, or the user asks), after step 4 (which ran at the start of the turn), give one block headed `Since last time`: per filed brief its ID and one line, the chores and backlog items added and the briefs parked (by ID), and one line naming by ID the `Discussing` items whose last entry is a question of yours (`board show <id>`). Nothing that needs no action. The open questions come here and not at every turn: a line repeated per turn is read past.
- "Show me the board": first make it current (step 4, then run each chore's check and `board done <id>` what is done), then say what changed, and the `Discussing` items with a question of yours open, in one line as at a pause. The lists themselves are in the user's board pane.
- A `blocked` question that needs the user cannot wait: the worker is idle on it. Ask at once, in its own block headed `Worker blocked on <id>`, separate from any design thread, with the options and a recommendation.
- A decision the user makes while a brief is in flight goes into the brief (`board amend <id>`) and to the worker as one line, so the filed brief matches what was built.

## Brief template

An amendment must not contain a `## ` line outside a code fence (use `###`): it would split the brief's section, and `board` refuses it. The worker's block question has the same rule (Worker protocol below).

The Task section holds the prompt or the finding only (Fresh read, above, defines the names), because the worker hands the fresh-eyes reviewer that section and nothing of the Design: whatever stands there is read as the intent the diff is judged against, so a summary of yours there makes the reviewer check the code against your story instead of the need. The prompt is the user's words that state the need, verbatim, each as it was said; a finding is a worker's words as the board records them (`board show <id>` of the brief it came from: an out-of-scope finding of its report, or a block question under its Questions), not the backlog line you wrote from it, which is yours. Before each quote one attribution line of yours (`owner, 2026-11-24:`, `a worker's finding in the report of brief 5 (backlog b3):`) says whose words follow, and that is all of yours there: no context paragraph, no paraphrase, no quote of the design, no approval ("brief it now", "1"). An answer of the user's to your question stands there only when it states a need their messages lack, under an attribution line that quotes the question; answers that only choose among your options are decisions, not intent: they go in the Design, marked as theirs with the date. Short words are no reason for context: they mean the need was never stated, so ask (Loop, step 1). `board` cannot tell the user's words from yours, so it does not try; the fresh read (above), which holds the source, does, unless it was skipped for a trivial brief.

`board new brief <slug>` writes the header (id, status, base); the body is:

```markdown
# <title>

## Task
<per prompt or finding, an attribution line (for an answer, one that quotes the question it answers), then its words verbatim: the user's words that state the need, or a worker's finding as the board records it; nothing of yours>

## Design
<approved decisions (the user's answers that only choose among your options among them, marked as theirs with the date), every other choice marked as the planner's choice, and the rejected alternatives the commit body should name>

## Premises
<what must still hold at HEAD; entry points, files>

## Out of scope
<what not to touch>

## Verification
<focused specs, lint>

## Not doable by the worker
<PROD checks and the like; these go in the report and the commit body>

## Worker protocol
- Start: `board next` gave you this brief. `git status` is clean and the premises hold at HEAD. Otherwise `board block <id> "<question>"` and don't improvise: the design was approved against those premises.
- Start, in place of the line above in a brief you park: `board next` gave you this brief. `git status` is clean, otherwise `board block <id> "<question>"`. When a premise does not hold at HEAD, do not block: `board report <id>` saying not built and which premise failed, send `reported: <id>`, and take the next brief in the same turn, as the Done line says. It was parked and released to run with nobody watching, and a block would hold the whole batch until a planner answers.
- Implement under the commit loop of the global CLAUDE.md. Non-trivial Design decisions get a decision comment in the code.
- Fresh-eyes review: give the reviewer only the Task section verbatim, the diff and the repo path, not the Design. The decisions are in the code; the reviewer judges the code against the words of the Task. Spawn the reviewer on the strongest model the session offers (the Agent tool's `model`), also when you run on a lesser one; if that one is unavailable (a usage limit), the next strongest, and the report and the commit body name the model the review ran on: the planner verifies the commit, not the diff, so this review is the only read the diff gets, and it costs a small share of the brief's tokens.
- Commit when green, without asking. One brief may be several commits, each with the trailer `Brief: <id>`. Never commit red.
```
